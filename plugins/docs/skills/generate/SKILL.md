# /docs generate - 앱 기술 문서 자동 생성

> 특정 앱의 코드베이스를 심층 분석하여, **사람과 AI 모두** 앱의 스펙/기능/동작 원리를 정확히 파악할 수 있는 기술 문서를 생성합니다.

## 문서의 목적

이 문서는 두 가지 핵심 독자를 위해 작성됩니다:

1. **사람** — 앱의 전체 구조, 비즈니스 로직, API 스펙을 빠르게 파악
2. **AI** — 코드 변경/수정 시 기존 로직, 의존 관계, 사이드 이펙트를 정확히 이해하고 안전하게 작업

따라서 모든 문서는 다음 질문에 답할 수 있어야 합니다:
- "이 기능은 **왜** 이렇게 동작하는가?"
- "이 부분을 변경하면 **어디에** 영향이 가는가?"
- "이 도메인의 **불변 규칙**(절대 위반하면 안 되는 규칙)은 무엇인가?"

## 핵심 원칙

- **예시 코드 금지**: 핵심 로직과 규칙만 서술, 예시 코드 작성하지 않음
- **Mermaid 시각화 필수**: 복잡한 개념, 구조, 흐름은 반드시 Mermaid 다이어그램으로 시각화 (layout: elk)
- **변경 영향도 명시**: 주요 컴포넌트/로직마다 변경 시 영향 범위를 기술
- **구현 의도 기록**: 단순히 "무엇을 하는가"가 아닌 "왜 이렇게 했는가"를 기록

## Mermaid 다이어그램 규칙

> **복잡한 개념은 반드시 다이어그램으로 시각화합니다.**

**가독성 규칙 (필수 준수):**
- 어두운 배경 → 밝은 글자 (#ffffff, #fef3c7, #e0f2fe)
- 밝은 배경 → 어두운 글자 (#1e293b, #166534, #92400e)

**권장 스타일:**
```mermaid
%%{init: {'theme': 'base', 'themeVariables': {
  'primaryColor': '#4f46e5',
  'primaryTextColor': '#ffffff',
  'secondaryColor': '#f0fdf4',
  'tertiaryColor': '#fef3c7'
}}}%%
```

**다이어그램 유형별 용도:**

| 다이어그램 | 용도 |
|-----------|------|
| flowchart (layout: elk) | 아키텍처 구조, 컴포넌트 관계, 의존성, 변경 영향도 |
| sequenceDiagram | API 요청-응답 흐름, 이벤트 처리 순서, 컴포넌트 간 호출 체인 |
| erDiagram | 데이터베이스 스키마, 엔티티 관계 |

| classDiagram | 도메인 모델, 패턴 구조, 인터페이스 계약 |

## 실행 단계

### 1단계: 대상 앱 확인

사용자에게 문서를 생성할 **대상 앱**을 확인합니다.
- monorepo인 경우 `apps/` 하위 디렉토리 목록 제시
- 단일 프로젝트인 경우 프로젝트 루트 대상

### 2단계: 앱 심층 분석

```
[분석 항목]
├── 기술 스택 (언어, 프레임워크, 주요 라이브러리)
├── 프로젝트 구조 (디렉토리 레이아웃, 레이어 구분)
├── 아키텍처 패턴 (Clean, Hexagonal, Layered 등)
├── API 엔드포인트 (라우터, 핸들러, 미들웨어)
│   ├── HTTP 메서드, 경로, 파라미터
│   ├── 요청/응답 스키마
│   └── 인증/인가 방식
├── 이벤트 시스템 (발행/구독, 핸들러)
│   ├── 이벤트 타입 및 페이로드
│   └── 이벤트 흐름
├── 데이터베이스
│   ├── 스키마/모델 정의
│   ├── 인덱스 전략
│   ├── 관계 (1:1, 1:N, M:N)
│   └── DB 엔진 특성 활용
├── 비즈니스 로직 (도메인 서비스, 유스케이스)
│   ├── 불변 규칙 (invariants)
│   ├── 의존 관계 및 호출 체인
│   └── 변경 시 사이드 이펙트
├── 타입/인터페이스 정의
└── 설정 및 환경 변수
```

### 3단계: 문서 구조 생성

`docs/{앱이름}/` 폴더에 문서를 생성합니다:

```
docs/{앱이름}/
├── overview.md                    # 앱 개요 및 빠른 이해 가이드
├── architecture.md                # 아키텍처, 패턴, 의존성 규칙
├── api-specification.md           # API 명세서 (API가 있는 경우)
├── event-specification.md         # 이벤트 명세서 (이벤트 시스템이 있는 경우)
├── database.md                    # DB 스키마, 인덱스, 데이터 흐름 (DB를 사용하는 경우)
├── business-logic.md              # 비즈니스 로직 및 도메인 규칙
└── tech-stack.md                  # 기술 스택 설명
```

## 문서별 작성 지침

### 1. Overview (`overview.md`)

앱을 처음 접하는 사람이나 AI가 **5분 안에 전체 그림을 파악**할 수 있는 진입점 문서입니다.

**필수 포함 항목:**
- 앱의 목적과 해결하는 문제
- 핵심 기능 목록 (각 기능의 한 줄 설명 포함)
- 시스템 내 위치 (다른 앱/서비스와의 관계 및 통신 방식)
- 주요 기술 스택 요약
- 프로젝트 디렉토리 구조 (각 디렉토리의 책임 설명)
- 핵심 용어 사전 (도메인 특화 용어 정의)

**필수 다이어그램:**
- 시스템 컨텍스트 다이어그램 (앱의 위치, 외부 시스템, 통신 방식)
- 프로젝트 레이어 구조 다이어그램

---

### 2. Architecture (`architecture.md`)

앱의 설계 철학과 구조적 제약을 설명합니다. AI가 코드 수정 시 **아키텍처 규칙을 위반하지 않도록** 하는 것이 핵심입니다.

**필수 포함 항목:**
- 채택한 아키텍처 패턴 명시 및 **선택 이유** (Clean Architecture, Hexagonal, Layered 등)
- 각 레이어의 역할과 책임
- 레이어 간 의존성 규칙 (의존성 방향, 의존성 역전 등)
  - **위반 시 발생하는 문제** 명시
- 주요 설계 패턴 (Repository, Factory, Strategy, Observer 등)
  - 각 패턴이 적용된 위치와 **왜 그 패턴을 선택했는지**
- 패키지/모듈 구조와 각 패키지의 책임
- 에러 처리 전략 (에러 전파 경로, 에러 변환 규칙)
- 미들웨어/인터셉터 체인 (실행 순서와 각 단계의 역할)
- **코드 변경 시 지켜야 할 규칙** (새 기능 추가 시 따라야 할 패턴, 금지 사항)

**필수 다이어그램:**
- 아키텍처 레이어 구조 및 의존성 방향 다이어그램
- 주요 설계 패턴별 구조 다이어그램
- 요청 처리 파이프라인 시퀀스 다이어그램 (요청이 어떤 레이어를 거쳐 처리되는지)

---

### 3. API Specification (`api-specification.md`)

앱이 제공하는 모든 API 엔드포인트의 완전한 명세서입니다.

**필수 포함 항목 (엔드포인트별):**
- HTTP 메서드, 경로
- 설명 및 용도
- 인증/인가 요구사항
- Path/Query/Body 파라미터 (타입, 필수 여부, 설명, 유효성 규칙)
- 성공 응답 스키마 (상태 코드, 필드별 타입과 설명)
- 에러 응답 스키마 (에러 코드, 메시지, 발생 조건)
- Rate Limiting 정책 (있는 경우)
- **내부 처리 흐름 요약** (어떤 서비스/핸들러를 거치는지)

**문서 구성:**
- 전체 API 경로 요약 테이블 (한눈에 모든 엔드포인트 파악)
- 리소스/도메인별로 그룹핑
- 각 그룹 앞에 개요와 공통 규칙 명시

**필수 다이어그램:**
- 인증/인가 흐름 시퀀스 다이어그램
- 복잡한 API의 내부 처리 시퀀스 다이어그램 (여러 서비스를 조합하는 경우)

---

### 4. Event Specification (`event-specification.md`)

앱 내부 및 외부로 발행/구독하는 모든 이벤트의 명세서입니다.

**필수 포함 항목 (이벤트별):**
- 이벤트 이름/타입
- 발행 조건 (언제, 어디서 발생하는지)
- 페이로드 스키마 (필드별 타입, 설명)
- 구독자/핸들러 목록과 각각의 처리 내용
- 에러 처리 및 재시도 정책
- **이벤트 순서 보장 여부** 및 **멱등성 처리 방식**

**문서 구성:**
- 전체 이벤트 목록 요약 테이블
- 도메인별로 그룹핑

**필수 다이어그램:**
- 이벤트 발행-구독 전체 맵 다이어그램
- 주요 이벤트 체인 시퀀스 다이어그램 (이벤트가 다른 이벤트를 트리거하는 경우)

---

### 5. Database (`database.md`)

데이터베이스 스키마, 인덱스 전략, 데이터 흐름을 상세히 문서화합니다.

**필수 포함 항목:**

**스키마:**
- 모든 컬렉션/테이블 목록과 용도
- 필드별 타입, 필수 여부, 기본값, 설명
- 관계 (1:1, 1:N, M:N) 및 참조 방식
- Embedded vs Referenced 전략과 **선택 이유** (NoSQL의 경우)
- Enum/상수 값 정의
- **스키마 변경 시 주의사항** (다른 컬렉션/테이블에 미치는 영향)

**인덱스 전략:**
- 모든 인덱스 목록 (필드, 타입, 옵션)
- 인덱스 설계 근거 (어떤 쿼리를 최적화하는지)
- 복합 인덱스의 필드 순서와 이유
- Unique, TTL, Partial, Text 등 특수 인덱스

**데이터 흐름:**
- 데이터 생성/수정/삭제 흐름
- 데이터 정합성 보장 방식 (트랜잭션, 이벤트 소싱 등)
- **데이터 간 의존 관계** (A 삭제 시 B에 미치는 영향)

**DB 특성:**
- 사용 중인 DB 엔진 및 선택 이유
- DB 엔진 고유 기능 활용 (Change Streams, Aggregation Pipeline 등)
- 마이그레이션 전략

**필수 다이어그램:**
- ER 다이어그램 (전체 엔티티 관계)
- 주요 데이터 흐름 다이어그램 (핵심 CRUD 작업의 데이터 경로)

---

### 6. Business Logic (`business-logic.md`)

앱의 모든 비즈니스 로직을 도메인별로 상세히 설명합니다. AI가 로직을 변경할 때 **기존 규칙을 파괴하지 않도록** 하는 것이 핵심입니다.

**필수 포함 항목:**
- 도메인별 비즈니스 규칙 목록
  - 각 규칙의 조건, 동작, 결과
  - **불변 규칙** (invariants): 어떤 상황에서도 반드시 유지되어야 하는 규칙을 별도 표시
- 유효성 검증 로직 (필드별 검증 규칙, 검증 시점)
- 상태 전이 규칙 (상태 머신이 있는 경우)
  - 허용되는 전이와 **금지되는 전이** 명시
- 계산/변환 로직 (금액 계산, 점수 산정 등의 공식과 근거)
- 권한/접근 제어 규칙
- 비즈니스 예외 처리 (도메인 에러 코드, 발생 조건, 처리 방법)
- **로직 간 의존 관계** (A 로직 변경 시 B 로직에 미치는 영향)

**필수 다이어그램:**
- 주요 비즈니스 프로세스 흐름 다이어그램
- 상태 전이 다이어그램 (상태 머신이 있는 경우)
- 복잡한 비즈니스 규칙의 의사결정 흐름 다이어그램

---

### 7. Tech Stack (`tech-stack.md`)

앱에서 사용 중인 주요 기술 스택과 **선택 배경**을 설명합니다.

**필수 포함 항목:**
- 프로그래밍 언어 및 버전
- 프레임워크 및 선택 이유
- 주요 라이브러리/패키지 목록 (용도별 분류)
- 데이터베이스 및 선택 이유
- 메시지 브로커/큐 (사용하는 경우)
- 인프라/배포 환경
- 개발 도구 (린터, 포매터, 테스트 프레임워크)
- 외부 서비스 연동 (결제, 알림 등)
- **기술 간 연동 관계** 및 **버전 호환성 제약**

**문서 구성:**
- 카테고리별 테이블 형식으로 정리 (기술명, 버전, 용도, 선택 이유)

**필수 다이어그램:**
- 기술 스택 레이어 다이어그램 (각 레이어에서 사용하는 기술과 연동 방식)

## 검증 단계

### 4단계: 자동 검증

```
[검증 항목]
├── 필수 문서 파일 생성 여부 (overview, architecture, business-logic, tech-stack은 필수)
├── 선택 문서 파일 적절성 (api-specification, event-specification, database는 해당 시스템이 있을 때만 생성)
├── 필수 섹션 포함 여부 (문서별 체크)
├── Mermaid 다이어그램 포함 여부 (문서별 필수 다이어그램 체크)
├── 예시 코드 미포함 확인
├── "왜" 관점의 설명 포함 여부 (설계 의도, 선택 이유)
├── 변경 영향도/주의사항 기술 여부
├── 내부 링크 유효성
└── 문서 간 용어 일관성
```

## 주의사항

> 기존 `docs/{앱이름}/` 폴더가 있으면 백업 후 진행합니다.

> 생성된 문서는 실제 코드베이스 분석 결과를 기반으로 작성됩니다. 코드에 없는 내용을 추측하여 작성하지 않습니다.

> 앱에 해당 시스템이 없으면 관련 문서는 생성하지 않습니다 (예: API가 없는 앱은 api-specification.md 미생성, 이벤트 시스템이 없으면 event-specification.md 미생성, DB를 사용하지 않으면 database.md 미생성).
