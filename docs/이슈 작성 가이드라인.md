## 1. 개요

이 문서는 개발 프로젝트의 이슈 작성 가이드라인입니다.

### 목적
- 일관된 이슈 작성으로 팀 커뮤니케이션 향상
- 프로젝트 진행 상황 추적 용이성 확보
- 명확한 작업 범위 정의로 효율적인 개발 진행

### 버전 표기 규칙
- **형식**: `YY.Q.N`
  - `YY`: 연도 (26 = 2026년)
  - `Q`: 분기 (1 = 1분기, 2 = 2분기, 3 = 3분기, 4 = 4분기)
  - `N`: 해당 분기 내 빌드 번호 (1, 2, 3...)
- **예시**: 
  - `26.1.1` = 2026년 1분기 1번째 빌드
  - `26.1.2` = 2026년 1분기 2번째 빌드
  - `26.2.1` = 2026년 2분기 1번째 빌드

## 2. 이슈 계층 구조

```
Initiative (이니셔티브)
  ↓
Epic (에픽)
  ↓
Task (작업) / Bug (버그)
  ↓
Sub-task (하위 작업)
```

### 계층별 특징

| 계층 | 용도 | 기간 | 담당 | 일정 관리 |
|------|------|------|------|----------|
| Initiative | 버전별 릴리즈 목표 | 2-6주 | PM/PO | 전체 기간만 명시 |
| Epic | 주요 기능 단위 | 4-5주 | Tech Lead | 주 단위 상세 일정 |
| Task | 개발 작업 단위 | 3-10일 | Developer | 시작일/종료일 |
| Sub-task | 최소 실행 단위 | 2-8시간 | Developer | 시작일/종료일 |
| Bug | 결함 수정 | 상황별 | Developer | 시작일/종료일 |

**참고**: 
- 1분기에 26.1.1, 26.1.2, 26.1.3 등 여러 버전이 릴리즈될 수 있음
- 각 버전마다 별도의 Initiative 생성

## 3. 이니셔티브 (Initiative)

### 정의
각 버전(빌드)별 릴리즈 목표를 정의하는 최상위 단위. 한 분기에 여러 개의 Initiative가 존재할 수 있음

**예시**:
- 26.1.1: 성능 개선
- 26.1.2: Azure/GCP 지원
- 26.1.3: AI 자동 최적화
- → 2026년 1분기에 3개의 Initiative

### 제목 형식
```
[YY.Q.N] 릴리즈 주요 목표
```

**예시**: `[26.1.2] Azure/GCP 멀티 클라우드 지원`

### 설명 구조

```markdown
## 배경
왜 이번 릴리즈가 필요한가?

## 목적
이번 릴리즈의 핵심 목표

## 주요 업무
### 카테고리 1
* 항목 1
* 항목 2

### 카테고리 2
* 항목 1
* 항목 2

## 기대효과
* 정량적 목표 1
* 정량적 목표 2

## 비고
* 릴리즈 일정: YY년 Q분기 (예: 2026년 1분기)
* 예상 개발 기간: N주
* 기타 참고사항
```

### 실제 예시

```markdown
## 배경

현재 SkuberPlus는 AWS EKS만 지원하고 있어 Azure/GCP 클라우드를 사용하는 Enterprise 고객 확보가 어려운 상황. 주요 경쟁사는 이미 멀티 클라우드를 지원하며 시장 점유율을 확대 중

## 목적

Azure AKS 및 GCP GKE 지원을 추가하여 SkuberPlus를 멀티 클라우드 비용 최적화 플랫폼으로 확장

## 주요 업무

### Azure 지원
* Azure AKS 클러스터 연동
* Azure Cost Management API 통합
* Azure-specific 리소스 최적화
* Azure 전용 대시보드 위젯

### GCP 지원
* GCP GKE 클러스터 연동
* GCP Cloud Billing API 통합
* GCP-specific 리소스 최적화
* GCP 전용 대시보드 위젯

### 공통 인프라
* 멀티 클라우드 추상화 레이어
* 통합 메트릭 수집 파이프라인
* 클라우드 프로바이더 선택 UI
* 멀티 클라우드 비용 비교 대시보드

### 문서 및 지원
* Azure/GCP 설치 가이드
* 클라우드별 Best Practices
* 마이그레이션 가이드 (AWS → Azure/GCP)

## 기대효과
* 크로스 클라우드 비용 비교 기능으로 경쟁 우위 확보

## 비고

* 릴리즈 일정: 2026년 1분기
* 예상 개발 기간: 12주 (3개월)
* AWS 기존 기능은 유지하며 호환성 보장
* Azure/GCP는 기본 기능부터 출시 후 점진적 확장
* Beta 테스트 참여 고객: 5개사 예정
```

## 7. 버그 (Bug)

### 정의
제품의 결함이나 예상과 다른 동작을 나타내는 이슈. RCA(Root Cause Analysis)를 통해 근본 원인을 파악하고 재발 방지

### 제목 형식
```
[YY.Q.N][영역] 버그 현상
```

**예시**: `[26.1.2][Azure] 비용 데이터 수집 시 타임아웃 발생`

```markdown
## 7. RCA - 5 Whys 분석

### Why 1: 왜 Azure Cost API 호출이 타임아웃되었는가?
**답변**: HTTP 클라이언트의 타임아웃 설정이 30초인데, 150개 리소스 쿼리는 평균 45초가 걸리기 때문

### Why 2: 왜 150개 리소스 쿼리가 45초나 걸리는가?
**답변**: Azure Cost Management API가 단일 요청에 모든 리소스의 상세 비용 데이터를 조회하고 집계하기 때문에 리소스 수에 비례하여 응답 시간 증가

### Why 3: 왜 타임아웃을 30초로 설정했는가?
**답변**: 초기 개발 시 소규모 테스트 환경(20개 리소스)에서만 테스트했고, 일반적인 HTTP 요청 타임아웃 기본값(30초)을 그대로 사용

### Why 4: 왜 대규모 Subscription 환경에서 테스트하지 않았는가?
**답변**: 테스트 계획에 다양한 규모의 환경 테스트 시나리오가 포함되지 않았고, 성능 요구사항에 "대규모 Subscription" 기준이 명시되지 않았음

### Why 5: 왜 프로덕션 배포 전에 이 문제를 발견하지 못했는가?
**답변**: 
- 통합 테스트가 자동화되지 않았음
- 성능 테스트에 다양한 규모의 시나리오가 없었음
- 프로덕션 모니터링에 API 응답 시간 알림이 설정되지 않았음

### 근본 원인 (Root Cause)

**기술적 원인**: 
- HTTP 클라이언트 타임아웃이 하드코딩되어 있고 대규모 쿼리를 고려하지 않음
- 단일 API 호출로 모든 리소스를 조회하는 비효율적인 구조

**프로세스 원인**:
- 성능 요구사항에 "대규모 환경" 기준이 누락
- 통합 테스트에 다양한 규모의 시나리오 부재
- 프로덕션 배포 전 성능 테스트 프로세스 미비

            results[i] = data

        })
    }

    }
```

## 10. 상태 관리

### ⚠️ 필수 규칙
작업 진행 상황을 정확히 파악하기 위해 상태 전환은 필수입니다.

- **작업 시작 시**: 반드시 "진행 중"으로 변경
- **작업 완료 시**: 반드시 "완료"로 변경

### 워크플로우

```
[생성] 해야 할 일 (To Do)
         ↓
    작업 시작 (필수 전환!)
         ↓
[진행] 진행 중 (In Progress)
         ↓
    선택적 중간 상태
         ↓
    ├─→ Development (개발 중)
    ├─→ Test (테스트 중)
    ├─→ Code Review (코드 리뷰 중)
    ├─→ Pending (외부 의존성 대기)
    └─→ Fix (버그 수정 중)
         ↓
    작업 완료 (필수 전환!)
         ↓
[완료] 완료 (Done)
```

### 상태별 의미

| 상태 | 의미 | 전환 시점 | 주의사항 |
|------|------|----------|---------|
| 해야 할 일 | 미착수 상태 | 이슈 생성 시 | 작업 시작 전까지 유지 |
| 진행 중 | 작업 진행 중 | **작업 시작 시 필수** | 실제 코딩/작업 시작 시 즉시 변경 |
| Development | 개발 단계 | 구현 작업 중 | 선택사항 |
| Test | 테스트 단계 | 테스트 작성/실행 중 | 선택사항 |
| Code Review | 코드 리뷰 단계 | PR 생성 후 | 선택사항 |
| Pending | 외부 대기 | 블로커 발생 시 | 블로커 내용 코멘트 필수 |
| Fix | 버그 수정 중 | 리뷰 피드백 반영 중 | 선택사항 |
| 완료 | 작업 완료 | **작업 완료 시 필수** | 모든 AC 충족 후 변경 |

## 부록 2: 레이블 사용 가이드

레이블은 **선택 사항**이지만, 이슈를 효율적으로 필터링하고 관리하는데 도움이 됩니다.

### 클라우드별 레이블

**aws**
- Amazon Web Services (EKS)
- 예시: EKS 클러스터 연동, AWS Spot Instance

**azure**
- Microsoft Azure (AKS)
- 예시: AKS 클러스터 연동, Azure Cost Management API

**gcp**
- Google Cloud Platform (GKE)
- 예시: GKE 클러스터 연동, GCP Cloud Billing API

**oci**
- Oracle Cloud Infrastructure (OKE)
- 예시: OKE 클러스터 연동, Oracle Cloud Cost 분석

**ncp**
- Naver Cloud Platform (NKS)
- 예시: NKS 클러스터 연동, NCP 비용 모니터링

**on-premise**
- 온프레미스 Kubernetes 클러스터
- 예시: 자체 구축 K8s, Bare Metal 클러스터 지원

### 영역별 레이블

**backend**
- 백엔드 API, 서비스 로직
- 예시: REST API, 비즈니스 로직, 데이터베이스

**frontend**
- 프론트엔드 UI/UX
- 예시: React 컴포넌트, 대시보드, 사용자 인터페이스

**agent**
- 클러스터 내 에이전트
- 예시: 메트릭 수집기, 최적화 엔진

**infrastructure**
- 인프라, 배포, DevOps
- 예시: CI/CD, 모니터링, 로깅

### 타입별 레이블

**feature** (기능)
- 새로운 기능 추가
- 예시: Azure 클러스터 연동, 멀티 클라우드 대시보드

**improvement** (개선)
- 기존 기능의 성능, UX 개선
- 예시: API 응답 속도 개선, UI 리팩토링

**refactoring** (리팩토링)
- 기능 변경 없이 코드 구조 개선
- 예시: 레거시 코드 정리, 아키텍처 개선

**patch** (패치)
- 버그 수정이나 소규모 보완
- 예시: 타임아웃 설정 수정, 로그 레벨 조정

**hotfix** (긴급 수정)
- 프로덕션 긴급 이슈 수정
- 예시: Critical 버그, 보안 취약점
