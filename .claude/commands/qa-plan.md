# /qa-plan - QA 계획서 생성

## 설명

QA 계획서를 **상세하게 작성**합니다.
테스트 범위, 전략, 일정, 성공 기준을 명확히 정의합니다.

---

## 사용법

```bash
/qa-plan                    # 계획서 생성
/qa-plan --edit             # 기존 계획서 수정
/qa-plan --from-prd         # PRD 기반 자동 생성
/qa-plan --from-worktree    # Worktree 기반 자동 생성
```

---

## 계획서 생성 프로세스

### Step 1: 정보 수집

**수집 항목:**

| 항목 | 소스 | 예시 |
|------|------|------|
| 프로젝트명 | package.json | "marketplace" |
| 기능 목록 | PRD, Worktree | 로그인, 결제, 검색 |
| 페이지 목록 | src/app | /login, /dashboard |
| 컴포넌트 | src/components | Button, Modal |

### Step 2: 테스트 범위 정의

**In-Scope (테스트 대상):**

```markdown
## 테스트 범위

### 포함
- 모든 사용자 대면 페이지
- 핵심 비즈니스 로직
- 폼 제출 및 유효성 검사
- 네비게이션 흐름
- 에러 처리

### 제외
- 관리자 페이지 (별도 QA)
- 외부 API 연동 상세
- 퍼포먼스 테스트
```

### Step 3: 테스트 전략 수립

**테스트 피라미드:**

```
        /\
       /E2E\        ← 10% (MCP Puppeteer)
      /------\
     / Integr \     ← 20% (API 연동)
    /----------\
   /    Unit    \   ← 70% (개별 함수)
  /--------------\
```

**Risk-based Testing:**

| 리스크 레벨 | 기능 예시 | 테스트 강도 |
|-------------|----------|------------|
| Critical | 결제, 인증 | 모든 시나리오 |
| High | 검색, 필터 | 주요 시나리오 |
| Medium | 설정, 알림 | 기본 시나리오 |
| Low | 도움말, 정보 | 스모크 테스트 |

### Step 4: 테스트 케이스 정의

**케이스 유형:**

| 유형 | 설명 | 예시 |
|------|------|------|
| Happy Path | 정상 흐름 | 올바른 로그인 |
| Edge Case | 경계 조건 | 빈 입력, 최대 길이 |
| Error Case | 에러 상황 | 잘못된 비밀번호 |
| Security | 보안 검증 | XSS, CSRF |

**Acceptance Criteria (Given-When-Then):**

```gherkin
Feature: 로그인
  Scenario: 정상 로그인
    Given 로그인 페이지에 접속
    When 올바른 이메일과 비밀번호 입력
    And 로그인 버튼 클릭
    Then 대시보드로 이동
    And 사용자 이름 표시
```

### Step 5: 성공 기준 정의

```markdown
## 성공 기준

### 필수 (Must Pass)
- [ ] P0 테스트 100% 통과
- [ ] Critical 버그 0개
- [ ] 모든 페이지 로드 확인

### 권장 (Should Pass)
- [ ] P1 테스트 95% 이상 통과
- [ ] Major 버그 모두 해결

### 선택 (Nice to Have)
- [ ] P2 테스트 90% 이상 통과
- [ ] 모든 Minor 버그 문서화
```

## 계획서 템플릿

```markdown
# QA 계획서

## 1. 개요

| 항목 | 내용 |
|------|------|
| 프로젝트 | {project_name} |
| 버전 | {version} |
| 테스트 기간 | {start_date} ~ {end_date} |
| 작성자 | Claude AI |
| 작성일 | {today} |

## 2. 목적

{프로젝트}의 프론트엔드 기능이 요구사항대로 동작하는지 검증합니다.

## 3. 테스트 범위

### 3.1 In-Scope
| 기능 | 페이지 | 우선순위 |
|------|--------|----------|
| 로그인 | /login | P0 |
| 회원가입 | /signup | P0 |
| ... | ... | ... |

### 3.2 Out-of-Scope
- {제외 항목 1}
- {제외 항목 2}

## 4. 테스트 전략

### 4.1 테스트 유형
- **E2E 테스트**: MCP Puppeteer 활용
- **스모크 테스트**: 핵심 기능 빠른 검증
- **회귀 테스트**: 버그 수정 후 재검증

### 4.2 테스트 환경
| 환경 | URL | 용도 |
|------|-----|------|
| Local | http://localhost:3000 | 개발 테스트 |
| Staging | https://staging.example.com | 통합 테스트 |

### 4.3 테스트 데이터
- 테스트 계정: test@example.com / password123
- 테스트 상품: PROD-001, PROD-002
- 테스트 결제: 4242-4242-4242-4242

## 5. 테스트 케이스 요약

| 우선순위 | 케이스 수 | 기능 |
|----------|----------|------|
| P0 | {count} | 로그인, 결제 |
| P1 | {count} | 검색, 필터 |
| P2 | {count} | 설정, 알림 |
| **Total** | **{total}** | |

## 6. 일정

| 단계 | 기간 | 활동 |
|------|------|------|
| 준비 | Day 1 | 환경 설정, 데이터 준비 |
| P0 테스트 | Day 1-2 | Critical 기능 테스트 |
| P1 테스트 | Day 2-3 | High 기능 테스트 |
| P2 테스트 | Day 3-4 | Medium 기능 테스트 |
| 버그 수정 | Day 4-5 | 버그 수정 및 재테스트 |
| 보고서 | Day 5 | 최종 보고서 작성 |

## 7. 리스크 및 대응

| 리스크 | 영향 | 대응 방안 |
|--------|------|----------|
| 서버 불안정 | 테스트 지연 | Local 환경 대체 |
| 테스트 데이터 오염 | 결과 신뢰도 하락 | 테스트 전 초기화 |

## 8. 성공 기준

### 8.1 테스트 통과율
- P0: 100%
- P1: 95%
- P2: 90%

### 8.2 버그 기준
- Critical: 0개
- Major: 해결 완료
- Minor: 문서화 완료
```
