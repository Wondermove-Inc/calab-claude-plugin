# 가설 기반 접근 (Hypothesis-Driven Problem Solving)

## 개요

**가설 기반 접근**은 과학적 방법론(Scientific Method)을 문제 해결에 적용하는 기법입니다.
관찰 → 가설 → 예측 → 실험 → 분석 → 결론의 과정을 통해 체계적으로 문제를 해결합니다.

---

## 사용 시점

- 원인이 여러 개일 수 있을 때
- 추측이 아닌 검증된 해결책이 필요할 때
- 실험으로 확인 가능한 문제일 때
- TDD 마인드셋으로 접근하고 싶을 때

---

## 6단계 프로세스

### Step 1: 관찰 (Observe)

문제 현상을 객관적으로 관찰합니다.

**관찰 포인트**:
- 에러 메시지
- 로그
- 사용자 행동
- 시스템 상태
- 재현 조건

**예시**:
```
관찰:
• 로그인 버튼 클릭 시 500 에러 발생
• 에러 메시지: "Internal Server Error"
• 모든 사용자에게 발생
• 배포 후 발생 시작
• 다른 API는 정상 동작
```

---

### Step 2: 가설 수립 (Hypothesize)

관찰을 바탕으로 원인에 대한 가설을 세웁니다.

**좋은 가설 조건**:
- 검증 가능해야 함
- 구체적이어야 함
- 반증 가능해야 함

**예시**:
```
가설 1: DB 연결 문제
가설 2: 인증 서비스 장애
가설 3: 새 코드의 버그
가설 4: 환경 설정 오류
```

**가설 우선순위**:
| 가설 | 가능성 | 검증 난이도 | 우선순위 |
|------|--------|------------|---------|
| 새 코드 버그 | 높음 | 쉬움 | 1 |
| 환경 설정 오류 | 중간 | 쉬움 | 2 |
| DB 연결 문제 | 낮음 | 쉬움 | 3 |
| 인증 서비스 장애 | 낮음 | 중간 | 4 |

---

### Step 3: 예측 (Predict)

각 가설이 맞다면 어떤 현상이 관찰될지 예측합니다.

**형식**: "만약 X가 원인이라면, Y를 확인했을 때 Z가 관찰될 것이다"

**예시**:
```
가설 1: 새 코드 버그
• 예측 1: 에러 로그에 새 코드 관련 스택 트레이스
• 예측 2: 이전 버전으로 롤백하면 문제 해결

가설 2: 환경 설정 오류
• 예측 1: 프로덕션/스테이징 설정 차이
• 예측 2: 환경 변수에 누락된 값

가설 3: DB 연결 문제
• 예측 1: 다른 DB 쿼리도 실패
• 예측 2: DB 연결 에러 로그 존재
```

---

### Step 4: 실험 (Experiment)

예측을 검증하는 실험을 수행합니다.

**실험 설계 원칙**:
- 하나의 변수만 변경
- 결과 측정 가능
- 재현 가능

**예시**:
```
실험 1: 에러 로그 분석
• 방법: 에러 발생 시점 로그 확인
• 결과: 새 코드(auth.service.ts:45)에서 에러

실험 2: 롤백 테스트
• 방법: 이전 버전으로 롤백
• 결과: 문제 해결됨

실험 3: 코드 분석
• 방법: auth.service.ts:45 라인 확인
• 결과: 새로 추가된 DB 쿼리에서 미존재 컬럼 참조
```

---

### Step 5: 분석 (Analyze)

실험 결과를 분석합니다.

**분석 질문**:
- 예측과 결과가 일치하는가?
- 가설을 지지하는 증거인가?
- 다른 해석이 가능한가?

**예시**:
```
가설 1 분석:
• 예측 1 ✅: 새 코드 스택 트레이스 확인
• 예측 2 ✅: 롤백 시 해결

→ 가설 1 채택: 새 코드의 버그가 원인

가설 3 분석:
• 예측 1 ❌: 다른 DB 쿼리는 정상
• 예측 2 ❌: DB 연결 에러 없음

→ 가설 3 기각
```

---

### Step 6: 결론 (Conclude)

분석 결과를 바탕으로 결론을 도출합니다.

**결론 유형**:
- **가설 채택**: 증거가 가설을 지지
- **가설 기각**: 증거가 가설을 반박
- **가설 수정**: 부분적으로 맞지만 수정 필요
- **추가 실험 필요**: 결론 내리기 어려움

**예시**:
```
결론:
• 채택된 가설: 새 코드의 버그
• 근본 원인: auth.service.ts의 DB 쿼리가
           미존재 컬럼(last_login_at) 참조
• 해결책: 컬럼 추가 마이그레이션 실행 또는 쿼리 수정
```

## TDD와의 연관성

가설 기반 접근은 TDD와 유사한 사고방식입니다:

| 가설 기반 | TDD |
|----------|-----|
| 관찰 | 요구사항 분석 |
| 가설 | 테스트 케이스 설계 |
| 예측 | Expected 결과 정의 |
| 실험 | 테스트 실행 |
| 분석 | 테스트 결과 확인 |
| 결론 | 리팩토링/수정 |

## 가설 검증 템플릿

```markdown
# 가설 검증 기록

## 문제
{문제 설명}

## 관찰
- {관찰 1}
- {관찰 2}

## 가설 목록

### 가설 1: {가설 제목}
- **가설**: {가설 설명}
- **가능성**: 높음/중간/낮음
- **예측**:
  - 만약 이 가설이 맞다면, {예측 1}
  - 만약 이 가설이 맞다면, {예측 2}
- **실험**:
  - 방법: {실험 방법}
  - 결과: {결과}
- **결론**: ✅ 채택 / ❌ 기각 / 🔄 수정 필요

### 가설 2: {가설 제목}
...

## 최종 결론
- **채택된 가설**: {가설}
- **근본 원인**: {원인}
- **해결책**: {해결책}
```

## 관련 방법론

- **5 Whys**: 가설 수립 전 빠른 원인 추적
- **RCA**: 더 체계적인 분석 프레임워크
- **A/B 테스트**: 해결책 검증에 활용
