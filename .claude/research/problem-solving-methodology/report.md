## 1. 핵심 요약 (Executive Summary)

> **한 줄 요약**: 효과적인 문제 해결은 체계적인 방법론(5 Whys, RCA, 가설 기반 접근)을 통해 근본 원인을 찾고, 구조화된 프로세스로 해결책을 검증하는 것이다.

### 3줄 요약
1. **정의**: 문제 해결 방법론은 증상에서 근본 원인을 찾아가는 체계적 프로세스
2. **목적**: 임시 방편이 아닌 근본적 해결로 재발 방지 및 시간 절약
3. **효과**: AI 지원 디버깅은 87% 성공률, 40% 빠른 버그 해결 달성

## 2. 주요 발견 사항 (Key Findings)

### 핵심 방법론 (7개)

| # | 방법론 | 설명 | 적용 시점 | 중요도 |
|---|--------|------|----------|--------|
| 1 | **5 Whys** | 반복적 "왜?" 질문으로 근본 원인 도출 | 원인 불명확 시 | ⭐⭐⭐ |
| 2 | **Root Cause Analysis (RCA)** | 체계적 근본 원인 분석 프로세스 | 복잡한 문제 | ⭐⭐⭐ |
| 3 | **가설 기반 접근 (Scientific Method)** | 관찰→가설→실험→분석→결론 | 모든 문제 | ⭐⭐⭐ |
| 4 | **Decision Tree / Troubleshooting Tree** | 단계별 진단 플로우차트 | 반복적 문제 | ⭐⭐ |
| 5 | **Binary Search / Divide & Conquer** | 이분 탐색으로 문제 범위 축소 | 코드 디버깅 | ⭐⭐ |
| 6 | **Fishbone Diagram (Ishikawa)** | 원인-결과 시각화 (6M 분석) | 다중 원인 | ⭐⭐ |
| 7 | **ITIL Problem Management** | Incident(복구) vs Problem(근본 해결) 구분 | 운영 환경 | ⭐ |

### 핵심 인사이트

```
문제 해결의 가장 중요한 점:

1. 증상(Symptom)과 원인(Cause)을 구분해야 한다
2. 근본 원인을 찾기 전에 해결책을 적용하면 재발한다
3. 가설을 세우고 검증하는 과정이 가장 효율적이다
4. 문제를 작은 단위로 분해하면 해결이 쉬워진다
5. 체계적 기록은 미래 문제 해결 시간을 단축한다
```

## 3. 상세 분석

### 3.1 5 Whys 기법

**개념**: Toyota Production System에서 개발된 반복적 질문 기법

**프로세스**:
```
문제: 서버가 응답하지 않음
  ↓ Why?
원인 1: 메모리 부족
  ↓ Why?
원인 2: 메모리 누수 발생
  ↓ Why?
원인 3: 이벤트 리스너 해제 안됨
  ↓ Why?
원인 4: cleanup 함수 미구현
  ↓ Why?
근본 원인: 코드 리뷰 체크리스트에 리소스 해제 항목 없음
```

**장점**:
- 단순하고 직관적
- 별도 도구 불필요
- 표면적 원인을 넘어 근본 원인 도출

**주의사항**:
- 5번이 정답이 아님 (3~7번 유동적)
- 다중 원인 시 여러 갈래로 분기 필요
- 추측이 아닌 사실 기반 답변 필요

---

### 3.2 Root Cause Analysis (RCA)

**개념**: 문제의 근본 원인을 체계적으로 분석하는 프로세스

**8단계 프로세스**:

```
1. 문제 정의 (Define the Problem)
   - 무엇이, 언제, 어디서, 얼마나 발생하는가?

2. 데이터 수집 (Collect Data)
   - 로그, 메트릭, 에러 메시지 수집

3. 원인 식별 (Identify Causes)
   - 5 Whys, Fishbone Diagram 활용

4. 근본 원인 확정 (Identify Root Cause)
   - 여러 원인 중 근본 원인 선정

5. 해결책 개발 (Develop Solutions)
   - 여러 해결책 제안 및 평가

6. 해결책 구현 (Implement Solutions)
   - 선택된 해결책 적용

7. 효과 검증 (Monitor Results)
   - 문제 재발 여부 모니터링

8. 문서화 (Document)
   - 전체 과정 기록 및 공유
```

---

### 3.3 가설 기반 접근 (Scientific Method)

**개념**: 과학적 방법론을 소프트웨어 문제 해결에 적용

**프로세스**:

```
1. 관찰 (Observe)
   "로그인 시 500 에러 발생"

2. 가설 수립 (Hypothesis)
   "DB 연결 타임아웃이 원인일 것이다"

3. 예측 (Predict)
   "DB 연결 시간을 늘리면 에러가 사라질 것이다"

4. 실험 (Experiment)
   타임아웃 설정 변경 후 테스트

5. 분석 (Analyze)
   결과 확인 - 에러 지속/해결 여부

6. 결론 (Conclude)
   가설 채택/기각, 새 가설 수립
```

**TDD와의 연관성**:
- 테스트 작성 = 가설 수립 + 예측
- 테스트 실행 = 실험
- 결과 확인 = 분석 + 결론

---

### 3.4 Decision Tree / Troubleshooting Tree

**개념**: 단계별 의사결정으로 문제 진단

**구조**:
```
[시작: 문제 발생]
    ↓
[질문 1: 에러 메시지가 있는가?]
    ├── Yes → [에러 코드 확인] → [해결책 A]
    └── No → [질문 2: 최근 변경사항?]
                ├── Yes → [변경 롤백] → [해결 확인]
                └── No → [질문 3: ...]
```

**장점**:
- 96%의 불필요 정보 제거 (Half-Splitting)
- 초보자도 체계적 진단 가능
- 반복 문제에 대한 지식 축적

---

### 3.5 Binary Search Debugging

**개념**: 코드를 이분 탐색하여 문제 범위 축소

**적용 예시**:
```
1. 전체 코드 100줄 중 버그 존재
2. 50줄 지점에 breakpoint → 정상
3. 75줄 지점에 breakpoint → 에러
4. 62줄 지점에 breakpoint → 정상
5. 68줄 지점에 breakpoint → 에러
6. 65줄에서 버그 발견!
```

**시간 복잡도**: O(log n) - 100줄 코드에서 7번 이내 발견

---

### 3.6 Fishbone Diagram (Ishikawa)

**개념**: 원인-결과를 시각화하는 도구 (6M 분석)

**6M 카테고리**:
```
                    ┌── Man (사람): 개발자 실수, 지식 부족
                    ├── Machine (기계): 서버, 인프라 문제
                    ├── Method (방법): 프로세스, 절차 문제
문제 ←──────────────┼── Material (자재): 데이터, 입력값 문제
                    ├── Measurement (측정): 모니터링, 로깅 부족
                    └── Milieu (환경): 환경설정, 외부 의존성
```

---

### 3.7 ITIL Problem Management

**Incident vs Problem 구분**:

| 구분 | Incident Management | Problem Management |
|------|--------------------|--------------------|
| 목표 | 서비스 즉시 복구 | 근본 원인 해결 |
| 시간 | 긴급 (분~시간) | 계획적 (일~주) |
| 접근 | 증상 해결 | 원인 분석 |
| 예시 | 서버 재시작 | 메모리 누수 수정 |

## 4. AI 지원 문제 해결

### 주요 통계
- **성공률**: 87%
- **시간 단축**: 40% 빠른 버그 해결
- **개발자 시간**: 50%가 디버깅에 소요

### AI 적용 영역
1. **패턴 인식**: 과거 유사 문제 자동 매칭
2. **로그 분석**: 대량 로그에서 이상 탐지
3. **코드 분석**: 잠재적 버그 자동 탐지
4. **해결책 제안**: 유사 문제의 해결 사례 추천

## 5. 통합 문제 해결 프로세스

### 제안: 6단계 통합 프로세스

```
┌─────────────────────────────────────────────────────────────┐
│  Phase 1: 문제 정의 (Define)                                 │
│  ─────────────────────────────────────────────────────────  │
│  • 증상 명확화: 무엇이, 언제, 어디서, 얼마나                    │
│  • 재현 조건 확인                                            │
│  • 영향 범위 파악                                            │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  Phase 2: 정보 수집 (Gather)                                 │
│  ─────────────────────────────────────────────────────────  │
│  • 로그, 에러 메시지, 스택 트레이스 수집                       │
│  • 최근 변경사항 확인 (git log, 배포 이력)                     │
│  • 환경 정보 수집 (버전, 설정, 의존성)                         │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  Phase 3: 원인 분석 (Analyze)                                │
│  ─────────────────────────────────────────────────────────  │
│  • 5 Whys로 근본 원인 추적                                   │
│  • Fishbone으로 다중 원인 시각화                              │
│  • Binary Search로 코드 범위 축소                            │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  Phase 4: 가설 검증 (Hypothesize)                            │
│  ─────────────────────────────────────────────────────────  │
│  • 가설 수립: "X가 원인이면 Y 현상이 발생할 것"                  │
│  • 실험 설계: 가설 검증 방법 정의                              │
│  • 테스트 실행 및 결과 분석                                   │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  Phase 5: 해결 (Solve)                                       │
│  ─────────────────────────────────────────────────────────  │
│  • 해결책 구현                                               │
│  • 테스트로 검증                                             │
│  • 사이드 이펙트 확인                                        │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  Phase 6: 문서화 (Document)                                  │
│  ─────────────────────────────────────────────────────────  │
│  • 문제-원인-해결책 기록                                      │
│  • 재발 방지책 수립                                          │
│  • 지식 베이스 업데이트                                       │
└─────────────────────────────────────────────────────────────┘
```
